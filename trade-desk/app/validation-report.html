5 November 2026 · Existing application and Netlify site

PAPER · live activation blocked. The strategy has not passed validation. No deposit, conversion, real order, withdrawal or transfer was made.

What has been implemented

The signed VALR order adapter, FOK entries with attached OCO stop-loss and take-profit, decimal sizing, fill verification, partial-fill handling, reconciliation, emergency reduction, duplicate protection and loss controls are implemented. The private journal and Stop New Trading control use a transactional PostgreSQL schema.

76 automated tests passed, including actual WebAuthn signature verification and a PostgreSQL-compatible integration test. Execution tests used simulated exchange responses; they do not confirm a real exchange stop or profitable strategy.

Forward paper trial

The existing Supabase project now holds a private, transactional paper journal. Each successful scheduled cycle records its public signals, market checks, policy hash, deployment and decision. The dashboard shows the actual first and latest observation. No observations are backfilled. Zero closed trades means no completed paper trade has yet been observed.

The journal service accepts server authentication only, rejects browser origins and live mode, and uses database lease fencing, unique signal IDs and compare-and-set state updates. Tables use row-level security in a private schema with no anonymous access. The Stop New Trading control persists across deployments.

Paper entries and exits use sampled public order books, assumed 0.07% per-side fees and a conservative funding reserve. Checks run every 15 minutes. Moves between observations can be missed, so these results cannot establish continuous stop execution or real exchange protection.

What remains before live trading

  1. A strategy with sufficient positive holdout evidence and at least seven days / 20 closed trades of forward paper evidence. These initial evidence thresholds are engineering defaults, not a guarantee of returns.
  2. The connected paper journal is operational on the existing database. Live execution still requires a separately reviewed PostgreSQL connection with the execution lock; the paper journal cannot store live intents or activate trading.
  3. Private verification of the TradeDesk subaccount, actual fees, futures enablement, 2× leverage, collateral and wallet accounting. The existing read-only credentials were preserved.
  4. Only after the evidence improves: a separate subaccount API key with View access and Trade, stored in Netlify secrets. No Withdraw, Internal Transfer or Link Bank Account permissions.
  5. Explicit approval of the dated capital, policy, deployment and activation record. Then one controlled minimum-size trade to verify actual fill, active exchange protection and final wallet reconciliation. The system suspends after that test for review before unattended operation.

The current release contains a code-level evidence check. Adding a trade key or changing an environment flag alone cannot bypass the failed validation.

Private configuration

Netlify → mrg-trade-desk → Project configuration → Environment variables. Keep all sensitive values marked secret and available only in Production. The current plan requires the combined Builds, Functions and Runtime scopes; the application never writes values into browser assets. Never send credentials in chat.

  • TRADEDESK_JOURNAL_URL and TRADEDESK_JOURNAL_TOKEN: configured server-only connection to the private PAPER journal. The token grants journal access only; it is not a Supabase database or service-role credential.
  • TRADEDESK_DATABASE_URL: TLS connection string to an approved existing PostgreSQL database after applying trade-desk/db/001_trading.sql through its supported migration workflow.
  • TRADEDESK_VALR_TRADE_API_KEY and TRADEDESK_VALR_TRADE_API_SECRET: a separate restricted subaccount key, only when activation prerequisites have passed.

Live authorisation and the database approval record remain unset. The dashboard cannot enable real orders.
